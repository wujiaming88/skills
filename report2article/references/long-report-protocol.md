# 超长报告处理协议

长报告同时有输入截断、输出截断、局部编辑破坏全局结构和对象内部信息漏失四类风险。必须先做全局设计，再分块落盘和按原子信息销账。

## 触发条件

满足任一条件即执行本协议：

- 报告对象数不少于 8 个；
- 正文约 6000 字或 8000 token 以上；
- 任一次读取出现截断或分页未完成。

## 第一步：完整读取并建立信息账本

分段读到原报告末尾，记录总行数或最后一节标题，确认不是只读到工具返回上限。

按 `info-checklist-template.md` 为全部原子信息编号：

- `O`：对象与适用范围；
- `F`：事实、事件与限定条件；
- `D`：数据、单位、日期与统计口径；
- `J`：判断、结论、归因和强弱；
- `L`：来源与去重后的唯一链接。

分别记下 O/F/D/J/L 总数。对象数量只是覆盖维度之一，不能代表对象内部事实、数据和判断已经保留。

## 第二步：先做全局结构

在写正文前完成：

1. 一句话读者主线；
2. 完整章节大纲；
3. 每章要回答的读者问题；
4. 每章覆盖的 O/F/D/J/L 编号；
5. 全文采用的语气、术语和简称；
6. 配图位置及其支撑编号。

这一步防止分块后各节各说各话。大纲可以调整，但编号移动时必须同步更新映射。

## 第三步：按章节分块编辑并落盘

- 每块以一个完整章节或一个清晰子问题为边界，不按固定字数硬切。
- 一次编辑一块，完成后立即写入输出文件并确认文件增长、尾部完整。
- 每块写入前回看相邻章节的结尾和开头，保持语气、术语和过渡一致。
- 导语和结尾可在主体完成后统一定稿，但其事实与判断同样必须关联编号。
- 分块是防截断措施，不是删减内容或降低每节深度的理由。

## 第四步：按原子信息逐块销账

每块落盘后更新映射表：

```text
章节二完成：O 3/8｜F 17/46｜D 8/20｜J 5/14｜L 6/12
本章覆盖：O03、F11-F17、D06-D08、J04-J05、L05-L06
```

检查重点：

- 编号必须对应文章中的准确落点，不能只凭对象名出现就销账。
- 同一信息跨章节重复时，只把主要承载位置作为落点，避免文章重复。
- 图表或图注承载了数据时，也要记录对应 D/L 编号。
- 当前块存在缺号、错配或判断漂移时，修正后才能进入下一块。

## 第五步：整体验收

### 正向覆盖

确认首次账本中每个 O/F/D/J/L 编号都有文章落点，且全部计数达到基线。

### 反向溯源

从文章开头逐段检查，确保正文、标题、过渡、结尾和配图中的事实与判断都能回到原报告编号。去重、改写和章节重排不能制造新关系。

### 独立二次派生

重新打开原报告，不复用第一次账本，从头二次派生完整的对象、事实、数据、判断和链接清单。将第二份清单与首次账本逐条比较：

- 第二份出现新原子信息：首次提取有遗漏，补账并补文章。
- 两份总数相同但内容不同：逐条核对，不以数量相等代替内容一致。
- 两份一致后，再执行最终正向覆盖与反向溯源。

## 搜索辅助的边界

字面搜索只适合验证对象名、精确数字、日期和 URL 是否出现。优先使用固定字符串匹配，例如：

```bash
rg -F -- "Vertex AI Agent Builder" article.md
rg -F -- "2026-06-11" article.md
rg -F -- "https://example.com/source" article.md
```

不要用对象标题数量推断完整信息覆盖，也不要让正则元字符改变搜索含义。判断强弱、因果、归因、限定条件和新增推论只能靠语义对读。

## 完成标准

只有首次账本、二次派生清单、文章映射和反向溯源一致时，才能报告：

```text
信息校验：O 个对象 / F 条事实 / D 个数据点 / J 条判断 / L 个唯一链接，全部可追溯 ✅
```
