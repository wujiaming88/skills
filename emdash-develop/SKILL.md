# Emdash 源码定制开发

目标：让定制功能自然融入 Emdash 的架构、视觉与交互，并交付可验证的代码或安装包。

官方源码：[generalaction/emdash](https://github.com/generalaction/emdash)。
产品文档：[emdash.com/docs](https://emdash.com/docs)。这是 Electron 桌面开发工具；`docs.emdashcms.com` 属于另一个项目。
参考快照：[本次核对的上游提交](https://github.com/generalaction/emdash/tree/ccc6cce4a41627deb6888db6763f3de5ff0e4e08)。参考页的 `main` 链接用于寻找最新资料，历史依据可在该提交下查看。

## 先定位目标版本

1. 确认用户指定的 checkout、分支、工作区改动和基线提交；已有 fork 就在其约定内工作，不自动升级、拉取或迁移到上游结构。
2. 读取目标仓库 `AGENTS.md`、适用的嵌套指令、`agents/README.md`（如有），再读取任务涉及的专题。用当前 `package.json`、锁文件、构建/测试配置与真实调用方核实路径、命令、依赖及行为。
3. 识别是 `apps/emdash-desktop` monorepo，还是应用位于仓库根目录的旧版；识别通信是 Wire 还是该分支原有 IPC/RPC。下方参考是 **2026-11-16、上游提交 `ccc6cce4a41627deb6888db6763f3de5ff0e4e08` 的导航快照**，不是所有版本的硬性目录契约。
4. 官网当前标注为 Emdash Classic 文档；公开文档可能落后于 checkout。例如官网曾列出 `pnpm run d`，本次源码已无该脚本。遇到冲突，说明差异，以目标版本实现和适用项目指令决定改法；不猜测 Emdash 2.0 未公开实现。

若只有需求而没有源码，先定位已有 checkout；确实没有时获取用户指定仓库到独立目录，不覆盖已有工作。只有项目身份或目标版本的歧义会改变实现时才询问。

## 执行流程

1. **定范围**：把需求转成用户可观察的结果、修改边界和验证标准。改代码前简述方案；存在实质取舍时，说明沿用现有机制与引入新机制的成本。
2. **找先例**：至少追踪一个相邻功能的入口、状态、服务/通信、UI 与测试。前端任务先找真实组件和页面/Storybook 先例，不能凭印象重画界面。
3. **最小实现**：在拥有该行为的模块改动。保留现有类型、错误处理、生命周期和平台边界。新功能添加行为测试；Bug 尽量先写失败复现。不要顺带替换状态库、UI kit、格式化工具或包管理器。
4. **分层验证**：先运行相关测试，再做范围匹配的类型、Lint、构建和用户流程验证。UI 必须实际渲染检查；打包必须检查产物本身。缺少环境时给出明确缺口，不把 mock 成功称为真实桌面、远程或发布验证。
5. **自查交付**：检查 diff、生成文件、配置兼容性与影响面。报告改了什么、验证结果、残余风险；打包附准确路径、平台/架构、签名与启动验证状态。

仅 Review 时先输出有证据的缺陷，不直接修改代码。仅打包时检查现有源码与构建链，不附带功能改动。开发任务是否需要打包取决于用户要求和变更风险。

## 贯穿约束

- TypeScript 保持 strict 与明确边界类型；不通过 `any`、非空断言或绕过 lint 规则掩盖状态问题。用简短中文注释解释新增的非显然约束，遵循现有命名与格式。
- 源码定制应保留上游可合并性；不把某次 fork 的补丁、用户目录、机器名、凭据或旧故障固化为通用需求。
- 仓库、worktree、终端、Agent 会话与 UI 视图各有生命周期；切换或卸载视图不意味着终止后台会话。
- 本地路径与远程路径须带正确 Host 语义；shell、PTY、SSH、认证、数据库、更新器相关改动读取对应风险文档。
- “开发/测试/打包”不自动扩展为发布安装包、推送代码、安装替换用户应用或修改生产更新源；按本次已有授权执行相应动作。
